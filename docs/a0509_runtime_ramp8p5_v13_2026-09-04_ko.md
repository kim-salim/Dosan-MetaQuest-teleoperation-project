# A0509 Multi-V2 ramp 8.5 v13 실증 계약

## 결론

v13은 기존 v12의 semantic, Dijkstra 비용, 122개 edge 및 bridge 형상을
변경하지 않고 실제 명령 계약만 opt-in으로 승격한다.

2026-09-04 사후 실증에서 사용자 분류 Level 1 다섯 종류와 Level 2 세 종류,
총 8개 task 종류가 각각 최소 1회 작업자 확인 성공했다. 이 결과는 v13의
물리 검증 갱신이며 알고리즘·registry topology·안전 계약을 바꾸지 않으므로
v14로 승격하지 않는다.

상세 성공 목록과 증거 등급은 다음 문서를 권위 기준으로 사용한다.
`docs/a0509_v13_validated_baseline_2026-09-04_ko.md`

- runtime profile: `a0509_ramp8p5_ack_span2_v1`
- linear ramp: `8.5 mm/tick`
- control rate: `30 Hz`
- per-axis hard velocity ceiling: `255 mm/s`
- bounded ACK lag: 최대 `1 command`
- acknowledged command span: `2 commands`
- 2-command XYZ axis span hard limit: `8.5 mm`
- 일정 속도 기준 ACK-safe axis envelope: `127.5 mm/s`

아래 한계는 완화하지 않았다.

- Cartesian norm velocity: `300 mm/s`
- command acceleration: `4000 mm/s²`
- command jerk: `4000 mm/s³`
- integrated squared jerk: `10,000,000`
- orientation ramp: `1.25 deg/tick`
- workspace, tracking, MUX/Live authority 및 E-stop 절차: 변경 없음

이 수치는 Doosan 하드웨어 정격이 아니라 Task-C proposal/streamer 계약이다.

## 마지막 실패와 수정 범위

근거 run:
`/home/rvlab/a0509_web_runs/20260904_130143_311170_9b03e382eab1`

마지막 T2→T3 run은 bridge 생성과 실행에는 성공했지만 soft crossfade에서
다음 오류로 fail-closed 되었다.

```text
BEZIER_BRIDGE downstream pass-through contract failed:
linear_ramp=1.171,7.692,1.274
```

기존 admission은 연속 생성 명령의 최대 단일 축 step
`4.208498887656859 mm`만 검사했다. 실제 bounded pipeline에서는 ACK가 한
명령 늦을 수 있으므로 다음 proposal을 `cmd[k-1]`과 비교하며, 이때 두
명령 누적 Y span `7.692 mm`가 기존 7.5 한계를 넘었다.

v13에서는 soft crossfade admission도 bridge validator와 동일하게 모든
prospective 2-command XYZ/회전 span을 실행 전에 검사한다. 따라서:

- 마지막 `7.692 mm` 사례: v12/7.5에서는 사전 거부, v13/8.5에서는 허용
- `8.5 mm` 초과 사례: 단일 step이 8.5 미만이어도 사전 거부
- admission 이후 ACK 상태가 변한 사례: 기존 downstream pass-through
  검사에서 다시 fail-closed

## 버전 결합 및 혼용 방지

v13 레지스트리, compiled Multi-V2 plan, setup support manifest, rollout
strategy, ready event 및 GUI runtime environment에 같은 profile ID를
기록한다. 다음 불일치는 rollout 시작 또는 preflight에서 거부한다.

- v13 plan + 7.5 bringup
- v12 plan + 8.5 bringup
- plan profile ID + strategy profile ID 불일치
- 실제 ROS streamer ramp + strategy downstream contract 불일치
- ramp/ACK/가속도/jerk/회전 값 중 하나라도 profile과 불일치

기존 edge shadow는 더 엄격한 7.5 계약에서 얻은 오프라인 증거로 그대로
보존한다. v13은 그 증거를 재작성하지 않고, 현재 관측으로 만든 bridge와
crossfade를 8.5 계약으로 다시 검사한다.

## 첫 실증 실행

실행 중인 기존 bringup/GUI에는 새 코드를 hot-reload하지 않는다. Live OFF,
MUX DISABLED를 확인하고 두 프로세스를 새로 시작한다.

터미널 1:

```bash
cd /home/rvlab/Dosan-MetaQuest-teleoperation-project
source /home/rvlab/venvs/lerobot/bin/activate

MOTION_AUTHORIZATION=I_ACKNOWLEDGE_TASK_C_REAL_ROBOT_MOTION \
CONTROL_DRY_RUN=false \
./scripts/run_task_c_control_bringup_ramp8p5_v13.sh
```

터미널 2는 bringup 완료 후 기존과 동일하게 실행한다.

```bash
cd /home/rvlab/Dosan-MetaQuest-teleoperation-project
./scripts/apply_a0509_control_scheduling.sh
```

터미널 3:

```bash
cd /home/rvlab/a0509-semantic-dijkstra-gui
./start_control_gui_v13_ramp8p5.sh 8766 --enable-motion
```

첫 실증은 기존 성공 edge인 Level 2 `T2.acquire_from_floor →
T3.deliver_to_floor`로 제한한다. 먼저 재검증·컴파일 후 상태/API에서 다음을
확인한다.

```text
profile_id: a0509_ramp8p5_ack_span2_v1
linear_ramp_mm_per_tick: 8.5
axis_velocity_limit_mm_s: 255.0
acknowledged_command_span_steps: 2
ack_safe_axis_speed_envelope_mm_s: 127.5
```

Live OFF preflight가 실제 streamer의 8.5 설정까지 일치시킨 뒤에만 기존 웹
승인 절차로 실행한다.

- 작업자 판단상 안전 여유가 부족한 동작
